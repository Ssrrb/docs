# Events

*System · draft*

## Purpose

The inbox tells an account that a document was created or that a document changed its state. The inbox belongs to the central library. Each module publishes the events of its own documents.

The inbox holds no business content. It holds the identity of what happened and the read state of each account. The title, the number, and the amount of an item come from the document that the item names.

## Rules

### L2-28 — The inbox is common infrastructure

The inbox must belong to the central library. A module must not keep its own inbox.

### L2-29 — Creation produces an event

The creation of a document must produce one event.

### L2-30 — State change produces an event

Every change of the state of a document must produce one event.

### L2-31 — No enumeration of document types

The common infrastructure must not enumerate document types.

### L2-32 — No enumeration of business events

The common infrastructure must not enumerate business event types.

### L2-33 — Content of an event

An event must hold one identifier, one reference to a document, one action, the account that caused it, and one moment.

### L2-34 — No amount in an event

An event must not hold an amount of a document.

### L2-35 — No state in an event

An event must not hold the state of a document.

### L2-36 — Content resolved from the document

The application must resolve the title, the number, and the amount of an event from its document.

### L2-37 — Read state per account

The application must keep the read state of an event for every account separately.

### L2-38 — No deletion of an event

The application must not delete an event.

### L2-41 — Events inside the project folder

The application must store every event in the folder of the project that owns its document. The application must store the read state of an event in the folder of that project.

### L2-42 — The company view reads without storing

The company view must read the events of the folders of the projects of a construction company. The company view must not store an event. The company view must not store the read state of an event.

## Example

One approval produces one event. The event names the document and nothing else.

| Field of the event | Value |
|---|---|
| Identifier | `9b41-0c7d` |
| Reference to the document | Certificate `CERT-0007` |
| Action | Approved |
| Account | Bruno |
| Moment | The moment of the approval |

The inbox shows the title, the number, and the amount by reading the certificate. The event holds none of them.

## Example

A document that no longer exists leaves its events in the inbox. The item shows that the document is gone. The application must not delete the event.

## Notes

The rule L2-29 and the rule L2-30 hold every event that the inbox shows. A new kind of document needs no change in the common infrastructure. The rule L0-06 of `docs/foundations/principles.mdx` requires that behaviour.

The application records the account and the moment of every state change. The document `docs/system/permissions.mdx` holds that rule.

The rule L2-41 keeps every event in the folder of the project that owns its document. The rule L2-42 lets the company view read the events of every project without a store of its own. The rule L2-13 of `docs/system/persistence.mdx` keeps those records portable.

An event of a document that no longer sits in a folder that the company view reads stays out of the company view. The rule L2-38 holds the event.
