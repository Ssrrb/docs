# Permissions

*System · draft*

## Purpose

A capability is a permission to use one engine. The application holds two capabilities: the capability to use the ECMS and the capability to use the ERP.

The application holds no role. A role would be a set of capabilities that differs between accounts. Every account holds every capability.

The application holds several accounts. Each account has its own authentication and its own inbox.

## Rules

### L2-01 — Identity of a user

The application must require a local login before it creates a project or opens a project.

### L2-02 — Number of capabilities

The application must define exactly two capabilities: one for the ECMS and one for the ERP.

### L2-03 — Assignment of a capability

The application must assign each capability to a user account.

### L2-04 — Default grant

The application must grant every capability to a user account by default.

### L2-05 — Effect on the interface

The application must hide the interface of an engine when a user account holds no capability for that engine.

### L2-06 — No role

The application must not define a role.

### L2-07 — The first account

The application must create the first account when the application holds no account.

### L2-08 — No login before the first account

The application must not require a login while it holds no account.

### L2-09 — Any account creates another

Any account must be able to create another account.

### L2-10 — Record of a state change

The application must record the account and the moment of every state change of a document.

### L2-39 — Refusal at the capability

The application must refuse an operation on a document when the account holds no capability for the engine that owns that document.

### L2-40 — No refusal at the interface

The application must not refuse an operation through a state of the interface. A refusal must not depend on a hidden panel.

## Example

Two accounts of one company hold the same capabilities and separate inboxes.

| Account | Capabilities | Inbox |
|---|---|---|
| Ana | ECMS, ERP | Ana |
| Bruno | ECMS, ERP | Bruno |

Both accounts approve documents. The application holds no rule that separates the accounts that issue a document from the accounts that approve it.

An account holds no capability for the ECMS. The account opens a work unit of a project that the account can read. The application refuses to change the work unit. The work unit keeps its values.

| Capability of the account | The interface shows | The application does |
|---|---|---|
| ECMS, ERP | The panel of the work unit | The account changes the work unit. |
| ERP | No panel of the work unit | The application refuses. The work unit keeps its values. |

The second row states the rule L2-39. The rule L2-40 holds the refusal when the interface shows the panel.

## Notes

The application holds no server for the login. The document `docs/system/persistence.mdx` holds the storage of a credential.

A role is a deferred need. The document `docs/execution/roadmap.mdx` holds that work.

The rule L2-05 states a courtesy. The rule L2-39 states the refusal. The courtesy must not replace the refusal. The rule L2-40 holds the refusal when the courtesy fails.

The rule L2-40 lets a team drop a gate of the interface without opening a hole in the application. The team repairs the gate as a defect of the interface. The refusal stands without that repair.

The rule L0-07 of `docs/foundations/principles.mdx` states the refusal at the layer of the engines. The rule L2-39 applies that rule to a user account.

The read state of an inbox item belongs to an account. The document `docs/system/events.mdx` holds that rule.
