# Minimum viable product

*Product · draft*

## Purpose

The MVP is the first delivery of the application. This document states what the user can do in the first delivery. This document states what the user cannot do yet.

The application is a local desktop program. The program is a fork of VS Code. The user opens a project as a folder on the local disk. The user works without a network service.

The MVP serves one construction company in Paraguay. The construction industry is the only industry. The user is an engineer or an architect.

The engines ERP and ECMS arrive as two modules of the application. Both modules are installed of factory. The application has no gallery and no installer in the MVP. The document `docs/foundations/principles.mdx` holds the rules L0-04 and L0-05.

## The rules of the interface

### L3-01 — Local login

The application must ask for a login before it creates a project or opens a project. The login must not need a network service.

### L3-02 — Spanish interface

The application must show its interface in Spanish.

### L3-03 — One project at a time

The application must open one project at a time.

### L3-04 — Project folder

The application must show the folder of the open project in the file explorer of the window.

### L3-05 — Currency on screen

The application must show every amount in the currency of the project.

### L3-06 — Recommended value

Every question that the application asks must offer one recommended value.

### L3-07 — Budget grid

The application must show the budget of the project in a grid. The user must be able to add a line, change a line, and delete a line of the grid.

### L3-08 — Work unit of a line

The application must let the user name a work unit for a budget line. The application must leave that field empty when the user gives no work unit.

### L3-09 — Print

The application must print the budget of the project.

### L3-10 — No network

The application must not need a network service to create a project, to open a project, or to work with a budget.

## The template

The application creates a project from a template. The template asks the questions below. The template offers one recommended value for each question. The recommended values come from this table.

| Question | Recommended value |
|---|---|
| Name of the project | The name that the user types |
| Name of the obra | The name of the project |
| Purchasing flow policy | `con-partida` |
| Currency | Dollar |
| Tax rate | 10 |
| Surcharges | Not defined yet |
| Import a budget now | No |

The template writes the folder of the project and one budget file. The document `docs/system/persistence.mdx` holds the rules of that folder.

The recommended surcharges are not defined. The document `docs/execution/roadmap.mdx` holds that work as pending. Until the team writes them, the template must offer no surcharges at all.

### L3-11 — Questions of the template

The template must ask for the name of the project, the name of the obra, the purchasing flow policy, the currency, the tax rate, the surcharges, and whether to import a budget. The application must not ask for anything else.

### L3-12 — Import inside the template

When the user accepts the import in the template, the application must ask for a budget file before it writes the folder of the project.

## The workflow

The workflow below proves that the MVP works. The user starts at an empty folder and ends with a printed budget and a paid certificate.

| Step | The user does |
|---|---|
| 1 | Creates a project from the template. |
| 2 | Imports a budget from an Excel workbook, from a file of the engine, or from a BC3 file. |
| 3 | Names a work unit for the lines of the budget. |
| 4 | Raises a purchase request, when the policy requires one. |
| 5 | Raises a purchase order from that request or from a line of the budget. |
| 6 | Approves the purchase order. |
| 7 | Issues the purchase order and receives the inputs. |
| 8 | Issues an internal advance and approves the advance. |
| 9 | Issues a payment certificate that holds that advance, approves it, and pays it. |
| 10 | Prints the budget. |

### L3-13 — Each step

The application must let the user perform every step of the workflow above. The application must refuse a step that the purchasing flow policy of the project excludes.

### L3-14 — States without a button

The application must show the states `draft`, `issued`, `approved`, and `paid` of a document. The application must not show a button for the state `draft`. A document holds the state `draft` while the user edits it.

### L3-15 — Import formats

The application must import a budget from an Excel workbook, from a file of the engine, and from a BC3 file of the FIEBDC-3 standard.

### L3-16 — No chain from the engine

The application must not apply a surcharge chain that the project did not declare. The application must not apply the default chain of the engine.

## What the application does not do

The application does not do any of the following in the MVP.

| The application does not | Note |
|---|---|
| Offer a gallery of modules | The two engines arrive installed. |
| Charge for anything | The application holds no payment gateway. |
| Keep a stock of inputs | The price list holds prices, not quantities in a warehouse. |
| Run an accounting module | The roadmap holds that work. |
| Store anything on a network service | The roadmap holds cloud storage. |
| Serve a second company | The roadmap holds that work. |
| Serve another industry | The construction industry is the only one. |
| Store plans, photos, requests for information, or inspections | The roadmap holds that work. |
| Run on a phone | The application runs on a desktop. |
| Show a type of project | The policy belongs to the project. |

## What proves that the MVP works

The MVP works when the workflow above runs on a real budget of a real project of a real construction company, and when the printed budget shows the amount, the committed amount, and the available amount of every line.

## Notes

The document `docs/domain/budgets.mdx` holds the rules of a budget. The document `docs/domain/work-units.mdx` holds the rules of a work unit. The documents `docs/domain/purchase-requests.mdx`, `docs/domain/purchase-orders.mdx`, and `docs/domain/certificates.mdx` hold the rules of the documents of the workflow.

The document `docs/system/permissions.mdx` holds the rules of the login.

The purchase flow of the workflow above has no separation of duties. One user account issues and approves every document. The roadmap holds the work for a second role.
