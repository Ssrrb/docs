# Minimum viable product

*Product · draft*

## Purpose

The MVP is the first delivery of the application. This document states what the user can do in the first delivery. This document states what the user cannot do yet.

The application is a local desktop program. The program is a fork of VS Code. The user opens a project as a folder on the local disk. The user works without a network service.

The MVP serves one construction company in Paraguay. The construction industry is the only industry. The user is an engineer or an architect.

The engines ERP and ECMS arrive as two modules of the application. Both modules are installed of factory. The application has no gallery and no installer in the MVP. The document `docs/foundations/principles.mdx` holds the rules L0-04 and L0-05.

## The rules of the interface

### L3-01 — Local login

The application must ask for a login before it creates a project or opens a project. The login must not need a network service.

### L3-02 — First account

The application must ask for a name and a password when it holds no account. It must create the first account from what the user gives.

### L3-03 — Several accounts

The application must let any account create another account.

### L3-04 — Spanish interface

The application must show its interface in Spanish.

### L3-05 — One project at a time

The application must open one project at a time. The application must show the project view of that project. The company view is not an open project.

### L3-06 — Project folder

The application must show the folder of the open project in the file explorer of the window.

### L3-07 — Currency on screen

The application must show every amount in the currency of the project.

### L3-08 — Recommended value

Every question that the application asks must offer one recommended value.

### L3-09 — Budget grid

The application must show the budget of the project in a grid. The user must be able to add a line, change a line, and delete a line of the grid.

### L3-10 — Work unit of a line

The application must let the user name a work unit for a budget line. The application must leave that field empty when the user gives no work unit.

### L3-11 — Print the budget

The application must print the budget of the project.

### L3-12 — No network

The application must not need a network service to create a project, to open a project, or to work with a budget.

### L3-13 — Inbox

The application must show an inbox. The inbox must show one item for every event that the inbox holds.

### L3-14 — Inbox item opens the document

The application must open the document of an inbox item when the user selects the item.

### L3-15 — Independent read state

The application must mark an inbox item as read for the account that reads it. It must leave the item unread for every other account.

### L3-16 — Evidence of a measurement line

The application must let the user attach image files to a measurement line of an advance certificate.

### L3-17 — Formats of evidence

The application must accept JPG, PNG, and WebP files as evidence. It must refuse every other format.

### L3-18 — Certificate as a document

The application must print an advance certificate as one A4 PDF. The PDF must hold a cover, the contract when the certificate names one, the table of measurement with the previous quantity, the period quantity, the accumulated quantity, the unit price, the amounts, the totals with tax, and then the evidence of each line.

### L3-19 — Economic view of a work unit

The application must show the economic view of a work unit on the node of the work unit itself. The view must hold the budget, the committed amount, the executed amount, the measured amount, the available amount, the allocated indirect, and the total cost of that node.

### L3-20 — Contract control

The application must show the contract amount, the certified amount, the paid amount, and the available amounts of a subcontract contract.

## The company view

The company view is the interface that the user reaches when no project is open. The company view shows the information of every project of the construction company.

### L3-28 — Reach the company view

The application must let the user reach the company view. The company view must not open a project.

### L3-29 — List of projects

The application must show the projects of the construction company in the company view. The list must separate the active projects from the finished projects.

### L3-30 — Open a project from the company view

The application must open a project when the user selects it in the company view. The application must show the project view of that project.

### L3-31 — Inbox in the company view

The application must show the inbox in the company view. The inbox must show one item for every event of every project of the construction company. The inbox must show the events of the account that reads them.

### L3-32 — Cashflow report

The application must show a cashflow report in the company view. The report must show one row for every currency. The row must hold the money that entered, the money that left, and the net of that currency.

### L3-33 — Period of the cashflow report

The cashflow report must show one period. The application must let the user choose the period.

### L3-34 — Accounts of the company

The application must show the accounts of the construction company. The application must show the capability of each account.

### L3-35 — Finished project

The application must let the user mark a project finished.

## The template

The application creates a project from a template. The template asks the questions below. The template offers one recommended value for each question. The recommended values come from this table.

| Question | Recommended value |
|---|---|
| Name of the project | The name that the user types |
| Name of the obra | The name of the project |
| Purchasing flow policy | `con-partida` |
| Currency | Dollar |
| Tax rate | 10 |
| Surcharges | Not defined yet |
| Import a budget now | No |

The template writes the folder of the project and one budget file. The document `docs/system/persistence.mdx` holds the rules of that folder.

The recommended surcharges are not defined. The document `docs/execution/roadmap.mdx` holds that work as pending. Until the team writes them, the template must offer no surcharges at all.

### L3-21 — Questions of the template

The template must ask for the name of the project, the name of the obra, the purchasing flow policy, the currency, the tax rate, the surcharges, and whether to import a budget. The application must not ask for anything else.

### L3-22 — Import inside the template

When the user accepts the import in the template, the application must ask for a budget file before it writes the folder of the project.

### L3-23 — Import formats

The application must import a budget from an Excel workbook, from a file of the engine, and from a BC3 file of the FIEBDC-3 standard.

### L3-24 — No chain from the engine

The application must not apply a surcharge chain that the project did not declare. The application must not apply the default chain of the engine.

## The workflow

The workflow below proves that the MVP works. The user starts at the company view and ends with a paid certificate and a portable project folder.

| Step | The user does |
|---|---|
| 1 | Creates the first account, or signs in. |
| 2 | Reads the company view and the cashflow of the company. |
| 3 | Creates a project from the template. |
| 4 | Imports a budget from an Excel workbook, from a file of the engine, or from a BC3 file. |
| 5 | Declares the surcharges of the project. |
| 6 | Builds the tree of work units and names a work unit for the lines of the budget. |
| 7 | Reads the economic view of each work unit. |
| 8 | Raises a purchase request, when the policy requires one. |
| 9 | Raises a purchase order from that request or from a line of the budget. |
| 10 | Approves the purchase order and reads the committed amount of the line. |
| 11 | Issues the purchase order and receives the inputs. |
| 12 | Signs a subcontract contract that covers the lines of one kind of work. |
| 13 | Issues an advance certificate for a period and attaches the evidence to each line. |
| 14 | Approves the advance certificate. The budget shows the measured amount. The contract shows the certified amount. |
| 15 | Registers the payment of the certificate. The contract shows the paid amount. |
| 16 | Registers the collection that the client pays. |
| 17 | Returns to the company view and reads the inbox of every project. |
| 18 | Reads the cashflow of the company. |
| 19 | Prints the budget and the certificate. |
| 20 | Copies the folder of the project to another disk. |

### L3-25 — Each step

The application must let the user perform every step of the workflow above. The application must refuse a step that the purchasing flow policy of the project excludes.

### L3-26 — States without a button

The application must show the states of a document. The application must not show a button for the state `borrador`. A document holds the state `borrador` while the user edits it.

### L3-27 — Portable folder

The application must keep every record of the project inside the folder of the project, so that a copy of that folder holds the whole project.

## What the application does not do

The application does not do any of the following in the MVP.

| The application does not | Note |
|---|---|
| Offer a gallery of modules | The two engines arrive installed. |
| Charge for anything | The application holds no payment gateway. |
| Keep a stock of inputs | The price list holds prices, not quantities in a warehouse. |
| Run an accounting module | The roadmap holds that work. |
| Pay a worker | The application has no payroll. A contract of category `M.O.` pays a `socio`. |
| Keep one budget per work unit | The project holds exactly one budget. |
| Store anything on a network service | The roadmap holds cloud storage. |
| Serve a second company | The roadmap holds that work. |
| Serve another industry | The construction industry is the only one. |
| Store plans, requests for information, or inspections | The roadmap holds that work. |
| Run on a phone | The application runs on a desktop. |
| Show a type of project | The policy belongs to the project. |
| Convert one currency into another | The cashflow report holds one row for every currency. The rule L1-147 holds the conversion. |
| Keep a store of the company view | The company view reads the folders of the projects. The rule L2-42 holds the store. The index file holds the paths of the projects. |
| Share one project between several users | The MVP runs on the local disk. The roadmap holds cloud storage. |

## What proves that the MVP works

The MVP works when the workflow above runs on a real budget of a real project of a real construction company, when the printed budget shows the amount, the committed amount, and the available amount of every line, when the printed certificate shows the measurement and the evidence of a real period, when the company view shows every project that the company runs with its inbox and the cashflow of the money that entered and the money that left of every currency, and when a copy of the project folder opens on another computer with the same data.

## Notes

The document `docs/domain/budgets.mdx` holds the rules of a budget. The document `docs/domain/work-units.mdx` holds the rules of a work unit. The documents `docs/domain/purchase-requests.mdx`, `docs/domain/purchase-orders.mdx`, `docs/domain/subcontracts.mdx`, `docs/domain/certificates.mdx`, and `docs/domain/payments.mdx` hold the rules of the documents of the workflow. The documents `docs/domain/clients.mdx` and `docs/domain/collections.mdx` hold the rules of the client and the collection.

The document `docs/system/permissions.mdx` holds the rules of the accounts. The document `docs/system/events.mdx` holds the rules of the inbox. The document `docs/system/persistence.mdx` holds the rules of the folder.

The document `docs/domain/companies.mdx` holds the rules of an amount that crosses projects. The rules L1-144 to L1-147 keep the cashflow report in one currency per row. The rules L2-41 and L2-42 of `docs/system/events.mdx` keep the inbox of the company view inside the folder of each project.

The document `docs/decisions/certificate-chain.mdx` holds the reason why one document measures the work.
