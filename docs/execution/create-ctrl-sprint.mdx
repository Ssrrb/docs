## Objetivo

El usuario instala el CLI con `npm i -g @ctrlmas/ctrl` o usa la terminal integrada de Ctrl+. La distribución incluye el CLI con la aplicación. El CLI crea un workspace con su primera obra (work site). El CLI también vincula una carpeta local a un workspace existente.

El paquete npm incluye el launcher y el backend Node. Los paquetes opcionales incluyen la TUI Rust y el helper de autenticación. La publicación estable requiere verificar los instaladores en los tres sistemas operativos.

Los miembros de una organización de Clerk comparten la identidad. Los miembros comparten la configuración central. Cada miembro materializa la estructura en su computadora. La materialización usa los mismos identificadores. La réplica no crea otro proyecto.

## Contrato de carpetas local

El ejemplo muestra la estructura de la carpeta raíz:

```
<raíz>/
├── workspace.code-workspace
├── README.md
├── .ctrl/
│   └── workspace.json
├── archivos-compartidos/
│   └── README.md
└── obras/
    └── <obra-id>/
        ├── .ctrl/
        │   └── obra.json
        └── <motor>/
            └── <capacidad>/
                └── README.md
```

Reglas de la estructura:

- Las referencias internas usan rutas relativas.
- Los manifiestos identifican la empresa, la organización de Clerk, el workspace, las obras y la versión de la estructura.
- Los manifiestos distinguen los módulos elegidos de los módulos incorporados por dependencia.
- Las carpetas de módulos viven bajo `erp/` o bajo `ecms/`.
- Un motor aparece en una obra solo si el motor tiene capacidades seleccionadas.
- Los identificadores determinan los nombres de las carpetas.
- La configuración canónica no contiene rutas absolutas.
- La configuración canónica no contiene credenciales.
- Si el destino está ocupado, el CLI rechaza la operación.
- El CLI acepta un destino ocupado si el destino tiene una operación pendiente reconocida.
- La recuperación preserva los archivos ajenos a la estructura.
- Los manifiestos registran el valor 1 en `schemaVersion`.
- Si la versión de la estructura es incompatible, el CLI rechaza la carpeta.
- El mensaje de rechazo indica actualizar el CLI.

## Interfaz del CLI

El bloque muestra el comando y sus opciones:

```
create-ctrl [directory]

Opciones:
  --name         Nombre del workspace nuevo
  --obra-name    Nombre de la primera obra
  --obra-code    Código de la primera obra
  --org          Identificador de la organización de Clerk
  --modules      Lista de las capacidades seleccionadas
  --workspace    Identificador del workspace existente para la vinculación
  --api-url      URL base de la API
  --auth-cli     Comando del helper de autenticación
  --advanced     Permite editar la configuración y las sugerencias empresariales
  --pull         Trae todos los workspaces de la empresa seleccionada
  --manage-org   Abre el portal de la organización en Clerk
  --yes          Acepta los recomendados sin preguntas
  --json         Produce un documento JSON en stdout
  --help         Muestra la ayuda
  --version      Muestra la versión del paquete
```

Reglas del comportamiento:

- La opción `--workspace` vincula una carpeta local a un workspace existente.
- La opción `--workspace` es incompatible con las opciones de modificación.
- La opción `--manage-org` es incompatible con la creación, la vinculación y el destino.
- Con la opción `--json`, `--manage-org` devuelve la organización, el rol y la URL del portal.
- Si la selección de módulos está vacía, la opción `--yes` acepta los recomendados.
- La opción `--json` no hace preguntas.
- La opción `--json` no inicia el login interactivo.
- Con la opción `--json`, stdout contiene un solo documento JSON.
- Con la opción `--json`, los diagnósticos salen por stderr.

| 0 | Éxito |
| 1 | Fallo de la ejecución |

## Protección del servicio

La API mantiene el registro abierto y exige identidad y membresía vigentes en Clerk.
La API no recibe autorización implícita por ejecutarse desde Ctrl+.
El Worker usa límites nativos con contadores distintos para preview y producción.
El límite previo a Clerk permite 120 solicitudes por IP por minuto.
El límite de identidad permite 60 solicitudes por usuario verificado por minuto antes de consultar membresías.
Cada POST exige los límites de diez solicitudes por usuario y diez por organización por minuto.
La organización del contador procede de la membresía vigente.
Un identificador arbitrario de la URL no selecciona el contador de otra organización.
Los límites se aplican antes del acceso a la base de datos.
La ausencia de los bindings requeridos produce HTTP 503 antes de consultar Clerk.
Los fallos del servicio de limitación producen HTTP 503 en su punto de verificación.
La API mide el cuerpo real y rechaza más de 16 KiB con HTTP 413.
El rechazo de frecuencia produce HTTP 429 con `Retry-After: 60`.
El CLI interactivo espera de forma cancelable y reintenta una sola vez con la misma entrada.
El modo JSON informa el rechazo sin esperar.
Producción desactiva el dominio workers.dev y las URLs de preview.

La regla de borde prevista para la zona Free limita 60 solicitudes por IP en diez segundos.
La regla bloquea durante diez segundos las rutas `/v1/` y `/healthz`.
La expresión disponible en Free cubre esas rutas en todos los hosts de la zona.
El procedimiento consulta la regla existente y no reemplaza una regla ajena.
El procedimiento registra los identificadores para retirar solo la regla agregada.
La aplicación de esta regla requiere un token WAF limitado a la zona.
Los contadores del Worker son locales a cada ubicación de Cloudflare y tienen consistencia eventual.
Estos controles no garantizan que un ataque distribuido respete la cuota diaria de Workers Free.

Referencias de implementación:

- [Rate limiting bindings](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/)
- [Regla de borde mediante Rulesets API](https://developers.cloudflare.com/waf/rate-limiting-rules/create-api/)
- [Parámetros de la regla de borde](https://developers.cloudflare.com/waf/rate-limiting-rules/parameters/)

## Recuperación

La creación central y la materialización local tienen estados separados. El workspace queda disponible cuando la transacción central termina. El CLI verifica su carpeta antes de informar el éxito.

Un diario local registra la operación. El diario guarda la clave de creación, la entrada normalizada, los identificadores, el snapshot y la fase de la operación.

La reanudación no ejecuta otra creación central. La reanudación no modifica la configuración registrada. Si la entrada cambia, el CLI produce un error explícito.
