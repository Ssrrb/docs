# Sprint create-ctrl y workspaces compartidos

*Execution · draft*

Este documento especifica las decisiones confirmadas del sprint `create-ctrl`. El sprint entrega un CLI, una API y un contrato de carpetas local.

El contexto de los dos motores está en `docs/foundations/erp-ecms-architecture.mdx`. La jerarquía de módulos está en `docs/domain/module-hierarchy.mdx`. El flujo de trabajo del sprint sigue `docs/execution/agile-workflow.mdx`.

## Objetivo

El usuario ejecuta el CLI con `npx create-ctrl`. El CLI crea un workspace con su primera obra (work site). El CLI también vincula una carpeta local a un workspace existente.

Los miembros de una organización de Clerk comparten la identidad. Los miembros comparten la configuración central. Cada miembro materializa la estructura en su computadora. La materialización usa los mismos identificadores. La réplica no crea otro proyecto.

## Contrato de carpetas local

El ejemplo muestra la estructura de la carpeta raíz:

```
<raíz>/
├── workspace.code-workspace
├── README.md
├── .ctrl/
│   └── workspace.json
├── archivos-compartidos/
│   └── README.md
└── obras/
    └── <obra-id>/
        ├── .ctrl/
        │   └── obra.json
        └── <motor>/
            └── <capacidad>/
                └── README.md
```

Reglas de la estructura:

- Las referencias internas usan rutas relativas.
- Los manifiestos identifican la empresa, la organización de Clerk, el workspace, las obras y la versión de la estructura.
- Los manifiestos distinguen los módulos elegidos de los módulos incorporados por dependencia.
- Las carpetas de módulos viven bajo `erp/` o bajo `ecms/`.
- Un motor aparece en una obra solo si el motor tiene capacidades seleccionadas.
- Los identificadores determinan los nombres de las carpetas.
- La configuración canónica no contiene rutas absolutas.
- La configuración canónica no contiene credenciales.
- Si el destino está ocupado, el CLI rechaza la operación.
- El CLI acepta un destino ocupado si el destino tiene una operación pendiente reconocida.
- La recuperación preserva los archivos ajenos a la estructura.
- Los manifiestos registran el valor 1 en `schemaVersion`.
- Si la versión de la estructura es incompatible, el CLI rechaza la carpeta.
- El mensaje de rechazo indica actualizar el CLI.

## Catálogo de capacidades

El catálogo organiza las capacidades en dos motores. El ERP es el motor administrativo. El ECMS es el motor técnico. El catálogo tiene 18 capacidades de negocio.

La autenticación es infraestructura. La autenticación no cuenta entre las 18 capacidades. La autenticación viene incluida. Nadie desactiva la autenticación.

La versión inicial del catálogo es 1. Las filas del catálogo son definiciones inmutables. Un cambio de la estructura del catálogo requiere otra versión.

## Datos

El sprint agrega tres tablas nuevas: `workspaces`, `submodules` y `project_submodules`. El sprint agrega dos columnas nuevas en la tabla `projects`. Una columna referencia el workspace de la obra. La otra columna registra la versión del catálogo.

La tabla `workspaces` agrupa obras. La tabla `workspaces` guarda una clave de creación. La clave de creación es única por empresa. La tabla `workspaces` guarda un hash de la entrada. El hash respalda la idempotencia de la creación.

Las obras antiguas conservan el workspace nulo. Las migraciones son aditivas.

## API v1

La tabla lista las rutas de la API:

| Ruta | Propósito |
|---|---|
| `GET /healthz` | Verificación de salud del servicio |
| `GET /v1/organizations` | Organizaciones del usuario autenticado |
| `POST /v1/organizations/:orgId/company` | Creación del perfil de la empresa. Solo un administrador la ejecuta |
| `GET /v1/module-catalog` | Catálogo de submódulos |
| `GET /v1/organizations/:orgId/workspaces` | Workspaces de la organización |
| `POST /v1/organizations/:orgId/workspaces` | Creación de un workspace. La creación es idempotente por `creationKey` |
| `GET /v1/organizations/:orgId/workspaces/:workspaceId` | Snapshot (instantánea) canónico del workspace |

La API verifica los tokens OAuth del helper de autenticación mediante Clerk. La API verifica la membresía vigente en Clerk. La API reconcilia la caché `company_members`. Si Clerk no puede verificar el token, la API responde con un fallo temporal. La API nunca autoriza una solicitud con una fila antigua.

## Interfaz del CLI

El bloque muestra el comando y sus opciones:

```
create-ctrl [directory]

Opciones:
  --name         Nombre del workspace nuevo
  --obra-name    Nombre de la primera obra
  --obra-code    Código de la primera obra
  --org          Identificador de la organización de Clerk
  --modules      Lista de las capacidades seleccionadas
  --workspace    Identificador del workspace existente para la vinculación
  --api-url      URL base de la API
  --auth-cli     Comando del helper de autenticación
  --yes          Acepta los recomendados sin preguntas
  --json         Produce un documento JSON en stdout
  --help         Muestra la ayuda
  --version      Muestra la versión del paquete
```

Reglas del comportamiento:

- La opción `--workspace` vincula una carpeta local a un workspace existente.
- La opción `--workspace` es incompatible con las opciones de modificación.
- Si la selección de módulos está vacía, la opción `--yes` acepta los recomendados.
- La opción `--json` no hace preguntas.
- La opción `--json` no inicia el login interactivo.
- Con la opción `--json`, stdout contiene un solo documento JSON.
- Con la opción `--json`, los diagnósticos salen por stderr.

La tabla lista los códigos de salida:

| Código | Significado |
|---|---|
| 0 | Éxito |
| 1 | Fallo de la ejecución |
| 2 | Error de uso o de entrada |
| 130 | Cancelación por el usuario |

- El CLI invoca el helper con `shell: false`.
- El CLI invoca el helper con los comandos de la lista:

```
obra-auth session --json
obra-auth login --json
```

- Los tokens no aparecen en las salidas del CLI.
- Los tokens no aparecen en los manifiestos.

## Onboarding empresarial

Si la fila de `companies` falta, solo un administrador completa el perfil mínimo. El perfil mínimo tiene cuatro campos: el nombre, el país, la moneda y la zona horaria. El identificador legal es opcional. El onboarding usa la función SQL existente.

La tabla lista las sugerencias del perfil:

| Campo | Sugerencia |
|---|---|
| País | `PY` |
| Moneda | `PYG` |
| Zona horaria | `America/Asuncion` |

Reglas del onboarding:

- La creación del perfil es idempotente por `clerk_org_id`.
- En una carrera, la respuesta devuelve la referencia que ganó.
- El onboarding no modifica un perfil existente.
- El onboarding no crea una organización de Clerk como compensación.
- El onboarding no elimina una organización de Clerk como compensación.

## Recuperación

La creación central y la materialización local tienen estados separados. El workspace queda disponible cuando la transacción central termina. El CLI verifica su carpeta antes de informar el éxito.

Un diario local registra la operación. El diario guarda la clave de creación, la entrada normalizada, los identificadores, el snapshot y la fase de la operación.

La reanudación no ejecuta otra creación central. La reanudación no modifica la configuración registrada. Si la entrada cambia, el CLI produce un error explícito.

## Despliegue

El Worker tiene dos destinos: preview y producción. El dominio propuesto para producción es `api.ctrlmas.tech`.

El despliegue sigue este orden:

1. Aplicar las migraciones y las políticas RLS en la base de datos de desarrollo.
2. Ejecutar la API y el CLI contra esa base de datos.
3. Desplegar el preview del Worker.
4. Construir y probar el tarball del paquete npm.
5. Reunir las evidencias y hacer la revisión.
6. Publicar el release.

Reglas del despliegue:

- El Worker no recibe las credenciales de migración.
- El CLI no recibe las credenciales de migración.
- El paquete público no contiene secretos.
